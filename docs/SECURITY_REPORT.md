# Expzip セキュリティ調査レポート

書庫を扱うソフトは、他人が作ったデータを解釈する。中身は信用できないものとして
扱わなければならない。この文書は、Expzip が既知の攻撃手法に対してどう作られているか、
どこがまだ確かめられていないかをまとめる。

| 項目 | 内容 |
|---|---|
| 対象 | コミット `ebcc34b` 時点のソースコード |
| 調べ方 | 実装の読み取り。攻撃書庫を用いた実地の検証は**行っていない** |
| 範囲 | 展開経路、書庫検査、配布形態、AI 連携 |

## 1. 既知の攻撃手法に対する耐性

### 1.1. Zip Slip (ディレクトリ・トラバーサル)

**対策済み。**

書庫内に `../../Windows/System32/cmd.exe` のようなパスを持たせ、展開先の外へ
書き出させる攻撃。二段構えで防いでいる。

1. **名前による判定** — `ArchivePath.IsEscaping` が、絶対パス、ドライブ指定 (`:` を含む名前)、
   および `..` で起点より上に遡るパスを弾く。展開先に依存しない判定なので、
   書庫を開いた時点の一覧表示でも同じ判定を使える。
2. **解決後の判定** — `Path.GetFullPath` で絶対パスにしたうえで、
   `ArchiveExtractor.IsInside` が展開先の配下にあることを確認する。

重要なのは、**この二段が展開の全経路に入っている**ことである。片方の経路だけ
素通りする、という取りこぼしがない。

| 経路 | 実装 |
|---|---|
| ZIP | `ArchiveExtractor.cs:90, 138` |
| 暗号化 ZIP | `ZipEncryption.cs:170, 211` |
| 7z / tar | `ExtractState.cs:58, 61` |

展開先そのものも `Path.GetFullPath` で正規化してから比較している。

### 1.2. シンボリックリンクを用いたトラバーサル (CVE-2025-11001 / CVE-2025-11002)

**影響を受けない。**

上位を指すリンクを先に作らせ、後続のエントリをそこ経由で書き込ませる攻撃。
Expzip には**リンクを解釈・作成する処理が存在しない**。書庫内のリンク項目は
通常のエントリとしてしか扱われないため、この手法は成立しない。

`symlink` / `reparse` / `junction` / `CreateSymbolicLink` を全ソースから検索して
該当が0件であることを確認した。

なお、**展開先の側に既にジャンクションが仕掛けられている場合**は別問題である。
`IsInside` は文字列の前方一致で判定しており、OS がリンクを解決した後の実体の
位置までは見ていない。攻撃者が事前に展開先を用意できる状況が要るため実際上の
危険は小さいが、対策していないことは記しておく。

### 1.3. Mark-of-the-Web の引き継ぎ (CVE-2025-0411 / CVE-2025-31334)

**対策済み。**

ネットから落としたファイルには `Zone.Identifier` という副ストリームが付く。
書庫から取り出したファイルにこれが引き継がれないと、SmartScreen や Office の
保護ビューが働かなくなる。

`MarkOfTheWeb.TryRead` で書庫の印を読み、`TryApply` で取り出したファイルに書き込む。
**書庫に印がある場合だけ引き継ぐ**ため、自分で作った書庫に不要な印は付かない。

肝心なのは適用範囲である。書庫の外へ実体が出る口は4つあり、
**すべてで印を読んでいる**。

| 口 | 実装 |
|---|---|
| 展開 | `MainWindow.xaml.cs:3731` |
| 書庫内のファイルをダブルクリックで開く | `MainWindow.xaml.cs:3441` |
| ドラッグして書庫の外へ取り出す | `MainWindow.xaml.cs:2984` |
| 自己解凍書庫を作る | `MainWindow.xaml.cs:2752` |

CVE-2025-0411 (7-Zip) が突いたのは2番目、**一時フォルダに出して開く経路**だった。
ここが塞がっていることに実質的な意味がある。

4番目は、出所の分からない書庫から作った実行ファイルが、素性の確かなものに
見えてしまうのを防いでいる。

## 2. 書庫検査機能 (#53〜#57)

Expzip は、展開する前に書庫を調べる機能を持つ。**21種類**を3系統で検査する。
攻撃的な書庫の多くは、展開前のこの段階で利用者に提示される。

### 2.1. 構造の検査 (#54)

壊れた書庫、細工された書庫を見つける。

`CrcMismatch` / `HeaderMismatch` / `Truncated` / `TrailingData` /
`UnsupportedMethod` / `DuplicateName` / `Unreadable` / `EncryptedNotChecked`

`HeaderMismatch` は、中央ディレクトリとローカルヘッダの食い違いを見る。
一覧に出る名前と実際に取り出される中身を別物にする細工に対応する。

### 2.2. 安全性の検査 (#55)

展開すると困ることが起きる書庫を見つける。

| 検査 | 何を防ぐか |
|---|---|
| `EscapingPath` / `SuspiciousPath` | Zip Slip (1.1 と同じ判定を共有) |
| `ZipBomb` / `HighRatio` | 展開爆弾。展開後が元の100倍を超えると報告する |
| `BidiOverride` | 右横書き記号による拡張子偽装 |
| `ExecutableExtension` | 開くと実行されうる拡張子 |
| `CaseCollision` | 大小文字だけ違う名前。展開先で片方が失われる |
| `ReservedName` / `TrailingSpaceOrDot` / `ControlCharacter` / `InvalidCharacter` | Windows で作れない名前、紛らわしい名前 |

`BidiOverride` は実際のマルウェア配布で使われてきた手口である。
`photo_gpj.exe` のような名前に右横書き記号を挟むと `photo_exe.jpg` に見える。

### 2.3. マルウェア検査 (#56)

Windows の AMSI に書庫内のファイルを渡し、導入済みの対策ソフトに判定させる。
`MalwareDetected` と `TooLargeToScan` の2つを報告する。

上限は 256MB (`AmsiScanner.SizeLimit`)。`AmsiScanBuffer` はバッファ全体を一度に
渡す必要があり、際限なく積むわけにいかないため上限を置いている。

**上限を超えたものは分割せず、「検査できなかった」と明示して報告する。**
分割すると署名が境目で切れて見落とすためで、黙って通すわけではない。
制限は 3.4 に記す。

## 3. 残る課題

### 3.1. 実行ファイルに署名がない — 優先度: 高

`Expzip.exe` と、同梱している自己解凍書庫のスタブ `sfx-x86.exe`、
ファイル結合用の `joiner-x86.exe` は、いずれもコード署名されていない。

```
NotSigned  Expzip.exe
NotSigned  sfx-x86.exe
NotSigned  joiner-x86.exe
```

**影響は本体のほうが大きい**。インストール不要の単体 exe として配る以上、
利用者は毎回 SmartScreen の警告を踏んで実行することになる。これが常態化すると、
本物のマルウェアの警告も同じ手つきで無視する癖がつく。また、配布物が途中で
差し替えられても、利用者に検知する手立てがない。

自己解凍書庫についても同じことが、それを受け取った第三者に起きる。

**判断: 現時点では署名しない (#74)**。証明書の費用と、OV では SmartScreen の
警告が実績を積むまで消えない点を踏まえ、見送ることを選んだ。

**見落としではなく、承知のうえで受け入れているリスクである**。配布規模が
広がる、改ざんの申し立てが起きる、または無償で証明書を得る道が確かめられた
場合に再検討する。

### 3.2. 未検証の解析コード — 優先度: 中

以下は本調査の対象外であり、**安全性を確認していない**。

- `NsisReader` / `NsisExtractor` — NSIS インストーラの解析 (#68)
- `ZipEncryption` — 暗号化 ZIP の復号
- `SharpArchiveReader` 経由の 7z / RAR 解析 (外部ライブラリ SharpCompress)

インストーラ形式や圧縮形式の解析は、細工されたヘッダを読む処理であり、
本質的に攻撃面である。

### 3.3. パスワードの平文保持 — 優先度: 低

一度入力したパスワードは、そのタブを閉じるまで `Dictionary<string, string>` に
平文で保持される (`MainWindow.xaml.cs:1523`)。`string` は変更できないため、
使い終わっても内容を消せず、回収されるまでメモリに残る。

プロセスメモリを読める攻撃者や、クラッシュダンプから漏れうる。ただし
**プロセスメモリを読まれた時点で他の防御も無意味**であり、優先度は低い。

### 3.4. AMSI の上限を超えるファイル — 優先度: 低

256MB を超えるファイルは検査されない。マルウェアに無意味なデータを足して
意図的に上限を超えさせれば、Expzip の事前検査は避けられる。

ただし、**避けられるのは Expzip の事前検査であって、OS の防御ではない。**
展開すればファイルは実際に書き込まれ、対策ソフトの実時間保護が掛かる。
加えて Expzip は「検査できなかった」と明示するため、利用者は
検査済みと誤認しない。

### 3.5. 一時展開ファイルの残留 — 優先度: 低

書庫内のファイルをダブルクリックで開くと、`%TEMP%\Expzip\session-*` に実体が
展開される。正常終了時は消える。

異常終了に備えて仕掛けがある (`TempWorkspace.cs`)。

- 置き場ごとに `FileOptions.DeleteOnClose` の錠ファイルを持つ。
  強制終了でもハンドルが閉じ、**錠だけは必ず消える**
- 次回起動時、錠の無い置き場を消し残しとみなして片付ける。
  稼働中の別インスタンスの置き場は猶予を置いて除外する

残るのは**異常終了した後、二度と Expzip を起動しなかった場合**である。
その間、平文のファイルがディスクに残る。

### 3.6. AI 連携で送信する内容 — 対処済み

書庫の作り方を推定する機能 (仕様書 10章) は、外部の AI に問い合わせる。
ファイルの中身は送らないが、**ファイル名とフォルダ構成は送る**。名前自体が
機密になりうる。無料枠の API では、送った内容が提供元の製品改善に使われる
可能性がある。

**設定画面にこの旨を明記済み**であり、機能は既定で無効、利用者が接続先を
設定して初めて動く。

関連して、**書庫内のファイル名がそのまま AI への指示文に入る**ため、
細工した名前でモデルを誘導する余地がある。これに対しては、
**AI の出力を信用せず必ず手元で検証する**作りになっている。

- `RuleEstimator` — 返ってきたルールをお手本書庫に対して**再検査**し、
  実際に成立するものだけ採用する (`RuleEstimator.cs:67`)
- `RuleNamer` — 提案された名前を **`RuleFixer.WhyNot` で全件検証**してから使う
  (`RuleNamer.cs:76`)

誘導が成功しても、成立しないルールや不正な名前は手元で落ちる。

## 4. この調査で見ていない範囲

以下は未着手である。安全だと確認したわけではない。

- 攻撃書庫を実際に作って通す**実地の検証**。本調査は実装の読み取りのみ
- 3.2 に挙げた解析コード
- 外部ライブラリ (SharpCompress、BouncyCastle) 自体の脆弱性と、その追随体制
- 書庫の**書き込み**側 (`ZipArchiveWriter` / `ZipEncryptedWriter` / `SfxWriter`)
- 分割書庫の結合処理 (`SplitVolumes` / `ConcatStream`)
