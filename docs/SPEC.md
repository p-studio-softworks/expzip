# Expzip 仕様書 v0.2

> このファイルは、開発で使っている仕様書のコピーである。正本は非公開の課題管理システムに置いてあり、
> そちらでは各機能からチケットへのリンクが張ってある。文中の `#123` はそのチケット番号。

## 1. 概要

| 項目 | 内容 |
|---|---|
| 名称 | Expzip |
| コンセプト | エクスプローラーライクなUIで書庫をブラウズ・操作できるアーカイバ |
| 配布形態 | インストール不要のポータブルアプリ(単一exe) |
| 対象OS | Windows 10/11 (x64) |
| ライセンス/利用形態 | フリーウェア(業務利用を含め完全無償)。ソースコードはMITライセンスで公開 |

## 2. フェーズ分け(スコープ管理)

| フェーズ | 内容 | 状態 |
|---|---|---|
| フェーズ1 | 書庫の閲覧・展開・追加ができるExplorerライクなブラウザ(MVP) | 対象 |
| フェーズ2 | 書庫内直接編集(インプレースでのリネーム/削除/上書き保存) | 将来(確定) |
| フェーズ3 | 7z/tar対応、パスワード付きZIP対応、タブ表示対応、多言語対応(日英)、書庫検査 | 将来(確定) |
| フェーズ4 | AIによる書庫作成ルール推定と違反検出・自動修正(差別化機能) | 将来(構想、詳細は[11章](#11-フェーズ4構想-aiによる書庫作成ルール推定と自動修正)参照) |
| 保留 | シェル統合(右クリックメニュー、拡張子関連付け) | 対象外 |
| 非対応 | LZH形式(読み取りも含め非対応) | 対象外 |

判断根拠: LZHは現在ほぼ使われておらず、対応コストに見合わないため最初から除外する。シェル統合はレジストリ変更を伴い「インストール不要」の理念と相性が悪いため保留。

## 4. 技術スタック

- **言語/フレームワーク**: C# / .NET 10 (LTS、サポート2028年まで) + WPF
  - .NET 8はLTSサポートが2026年11月に終了するため採用しない
- **圧縮ライブラリ**:
  - ZIP: `System.IO.Compression`(標準)をベースに、Shift-JISファイル名対応のためエンコーディング処理を独自にラップ、またはSharpCompressで代替
  - 7z/tar等: [SharpCompress](https://github.com/adamhathcock/sharpcompress)(マネージド、ライセンス的にクリア)
  - パスワード付きZIP(AES-256)の書き込みは対応ライブラリに課題あり([7章](#7-既知の技術的リスク)参照)
- **配布方式**: 発行プロファイル `src/Expzip/Properties/PublishProfiles/win-x64.pubxml` を使用する
  - `dotnet publish src/Expzip -p:PublishProfile=win-x64` で `publish/win-x64/Expzip.exe` を生成
  - 単一exeとしてビルドし、フォルダにコピーするだけで動作させる
  - トリミング(`PublishTrimmed`)はWPFでは非サポートのため使用しない
  - 代わりに単一ファイル圧縮(`EnableCompressionInSingleFile`)を有効にする。**実測で134MB → 61.8MB**まで削減できた(v0.1.0時点)
  - レジストリ書き込み・インストーラは一切使用しない

## 5. UI設計

### 5.1 基本レイアウト(Explorerライク)

フェーズ1〜2は単一書庫のみを表示する構成。フェーズ3でタブバーを追加し、複数書庫を並行して開けるようにする(フェーズ4のAI機能は隣接タブ間の比較を前提とするため、タブ表示はその土台となる)。

```
┌─────────────────────────────────────────────┐
│ ツールバー(開く/新規作成/展開/追加/更新)         │
├─────────────────────────────────────────────┤
│ アドレスバー(書庫内の現在パス表示)                │
├─────────────────────────────────────────────┤
│ タブバー(フェーズ3以降。書庫ごとに1タブ、数の上限なし) │
├───────────────┬───────────────────────────┤
│ ツリービュー      │ リストビュー                    │
│ (書庫内フォルダ階層)│ (名前/サイズ/圧縮後/圧縮率/更新日時) │
│               │                              │
├───────────────┴───────────────────────────┤
│ ステータスバー(選択数/合計サイズ/進捗)              │
└─────────────────────────────────────────────┘
```

### 5.2 タブ仕様(フェーズ3〜)

- タブ数に上限は設けない
- 各タブはツリービューとリストビューの表示状態(展開位置、選択項目、ソート順など)を個別に保持する
- ステータスバー・タイトルバーは、現在アクティブなタブの書庫ファイル名に応じて表示内容が切り替わる

### 5.3 操作方法

- 書庫を仮想フォルダとしてツリー/リストに展開表示(実ファイルシステムのように振る舞う)
- 展開の対象は、一覧で選んでいる項目。**一覧で何も選んでいない場合は、いま開いているフォルダ**が対象になる(ツリーでフォルダを選んだ状態はこれに当たる)。ルートを開いている場合は書庫全体
  - 展開先を選ぶダイアログの見出しに対象を出す(「書庫全体の展開先を選択」/「選択した項目の展開先を選択」/「「〈フォルダ名〉」の展開先を選択」)
  - **選んだものが展開先の最上位に来る**。書庫のルートからの階層は作らない。`資料/画像` を選べば展開先には `画像\…` が並ぶ。書庫全体を展開する場合はこれまでどおり階層をそのまま作る
  - 上書きの確認は、**展開先に同じ名前のファイルが実際にある場合だけ**出す。件数と名前を挙げる
  - 親へ戻る `..` の行は置かない(エクスプローラーにも無い)。一つ上へはツリーか **BackSpace** で移動する
- リストビューの列ヘッダクリックでソート
- ダブルクリックでフォルダ移動 / ファイルは一時展開して既定アプリで開く(Enter キーおよび右クリックメニューの「開く」も同じ動作)
  - 一時展開先は `%TEMP%\Expzip\session-*`。exe と同じフォルダには置かない(持ち運び先が書き込み不可のことがあるため)
  - 一時展開したファイルはアプリ終了時に削除する。開いたままのアプリに掴まれていて削除できなかった分は、次回起動時に片付ける
  - 一時展開したファイルは読み取り専用にしない
  - **開いた先で保存されたら、書庫へ反映するか尋ねる**。「開く」と「編集」を分けない。どちらも既定のアプリに渡すだけで見た目が同じになり、違いが伝わらないため
    - 変更の検出は更新日時と大きさの組を1秒ごとに見る方式。保存の作法(その場で書き換える / 別名で書いてから置き換える)がアプリによって違い、後者では対象のファイルが一度消えて作り直されるため、ファイル監視ではなくパスを見に行く
    - 反映を「いいえ」で見送った変更は、**アプリ終了時に改めて尋ねる**。そこで「いいえ」を選ぶと変更は失われる
    - 反映せずに終わった場合、一時展開したファイルは終了時に消える
  - 実行されうる拡張子(`.exe` `.bat` `.vbs` `.lnk` など)は開く前に確認する。既定は「キャンセル」
  - 書庫に出所の印(Mark of the Web)が付いている場合は、書き出したファイルにも引き継ぐ。SmartScreen や保護ビューが働かなくなるのを防ぐため。一時展開だけでなく、**「展開」とドラッグアウトでも引き継ぐ**
- 名前の変更(F2 または右クリックメニュー)。**一覧の上でその場で書き換える**(エクスプローラー と同じ。ダイアログは出さない)。ファイルとフォルダの両方に対応し、フォルダは配下ごと付け替える
  - 開始は **F2 / 右クリックメニュー / 選択済みの項目の名前をもう一度クリック** の3通り(エクスプローラー と同じ)
    - クリックで始めるものは、ダブルクリックの2回目が来ないことを確かめてから始める。開くつもりの操作で入力欄が出ないようにするため。待つ長さは利用者の設定 (`GetDoubleClickTime`) に従う
    - 名前の列を押した場合だけ。サイズなど他の列を押しても始まらない
  - 拡張子を除いた部分だけを選んだ状態で始まる。Enter で確定、Esc で取り消し
  - **入力欄の外を押した時点で確定する**。一覧の余白など、フォーカスの移らない場所を押した場合も終わる
  - 同じフォルダに同名の項目がある場合、`\` `/` を含む場合、展開先で作れない文字を含む場合は変更しない
  - ZIPにはエントリ名だけを書き換える手段が無いため、**名前を変えた項目は圧縮し直される**。中身は変わらないが圧縮後のサイズは変わりうる。対象外の項目はそのまま持ち越す
- **書庫内での移動**。項目を掴んで、ツリーのフォルダまたは一覧のフォルダへ落とす
  - フォルダは配下ごと動く。複数まとめて動かせる
  - 移動先に同じ名前がある場合、元と同じ場所へ落とした場合、自分自身や自分の配下へ落とした場合は受け付けない
  - 名前の変更と同じ仕組みで、**動かした項目は圧縮し直される**
  - 外へ落とせば取り出し、中へ落とせば移動になる。ドラッグには書庫内の情報も載せてあり、Explorer はそれを無視して通常のファイルとして受け取る
- ドラッグ&ドロップ:
  - Explorer→書庫へのファイル追加: フェーズ1
  - 書庫→Explorerへのドラッグアウト(展開): 一時フォルダへ取り出してから標準のファイルドロップとして渡す(方式の選定は[7章](#7-既知の技術的リスク)参照)
    - 取り出し先と後片付けは「開く」と同じ置き場を使う
    - **ツリービューのフォルダも掴んで出せる**。ルート(書庫そのもの)を掴んだ場合は直下の項目をまとめて渡す
    - ドラッグの開始は同期処理で途中に進捗を挟めないため、**3,000件 / 512MB を超える選択では「展開」を使うよう促す**
    - 取り出したファイルは読み取り専用にしない。ドロップ先にそのままコピーされるため
- **ウィンドウに書庫を1つ落とすと、その書庫を開く**
  - 書庫を開いていない状態でも受け取る
  - 「落としたら開く」と「落としたら中に入れる」は両立しないため、開くほうを既定にする。**書庫を書庫の中に入れたい場合は Shift を押しながら落とす**。使う頻度は開くほうが高いという判断
  - 書庫以外、または複数のファイルを落とした場合は、これまでどおり追加する
  - 一覧の上だけでなく、ツリーやステータスバーの上に落としても受け取る
- **書庫の中に空のフォルダを作る**(右クリックメニューの「新しいフォルダ」または Ctrl+Shift+N)
  - 作る場所はいま開いているフォルダ。ツリーの節を右クリックした場合は、その節へ移ってから作る
  - 名前を尋ねるダイアログは出さず、`新しいフォルダー` として作ってその場で書き換えられる状態にする(エクスプローラーと同じ)。既にあれば `新しいフォルダー (2)` のように番号を付ける
  - ZIPはフォルダを明示的に持たなくてもよく、中身のあるフォルダはファイルのパスから組み立てられる。空のフォルダはそれでは表せないため、末尾が `/` のエントリを1件書き込む
- 右クリックコンテキストメニュー(アプリ内のみ。OSシェルへの統合はしない)
  - 一覧: 開く / 名前の変更 / 削除 / 新しいフォルダ。項目の上でも、何もない場所でも出る
  - ツリー: 新しいフォルダ

### 5.4 書庫検査(フェーズ3、#53)

ツールバーの「検査」から、開いている書庫をまとめて調べて1枚の報告にする。検査の種類ごとにメニューを分けない。利用者が知りたいのは「この書庫は安全に開けるか」の一点で、種類の区別は実装側の都合のため。

- **起動は手動のみ**。書庫を開くたびには走らせない(開く速さを損なうため)。開いた時点で出す「パスが通常ではない項目」の警告(#36)はこれまでどおり
- **見るもの**
  - 構造(#54): CRCの照合(全エントリを実際に展開して確認)、中央ディレクトリとローカルヘッダの食い違い、切り詰められた書庫、未対応の圧縮方式、重複するエントリ名
  - 安全性(#55): 書庫の外を指すパス、Windowsで作れない名前(`CON` `PRN`、末尾の空白やピリオド)、大文字小文字だけ違う衝突、右横書き記号(U+202E)による拡張子の偽装、圧縮率が異常なエントリ(ZIP爆弾)、実行されうる拡張子
  - マルウェア(#56): AMSI に各エントリの中身を渡す。書庫ファイル自身も渡し、入れ子の書庫は対策ソフト側に開いてもらう
- **結果**(#57): 「重大度 / 対象 / 内容」の一覧。行を選ぶとその項目へ飛ぶ。**問題が無かったことも明示する**(何も出ないと検査が働いたのか分からないため)
- **駆除・隔離・削除はしない**。報告して終わりにする。書庫の中身をどうするかは利用者が決めること
- CRC照合は書庫を丸ごと読むため、進捗と中断に対応する(#39 の仕組みに載せる)

## 7. 既知の技術的リスク

- **文字コード問題**(#13で検証済み、方式決定): ZIP仕様上、ファイル名のエンコーディングは一意に定まらない。EFSフラグ(汎用フラグbit11)が立つエントリはUTF-8だが、立たないエントリは本来CP437であり、日本語圏の既存ツールはそこにCP932を書いてきた。日本語の書庫を扱うアーカイバでは、この判別精度が使い勝手を大きく左右するので、妥協できない箇所。
  - **採用方式**: `ZipArchive` の `entryNameEncoding` にカスタム `Encoding` を渡し、フラグなしエントリを「UTF-8として厳密に妥当ならUTF-8、そうでなければCP932」と判定する。フラグ付きエントリは.NETが常にUTF-8として扱うため干渉しない
  - **判定はエントリ単位**で行う。同一書庫内でもフラグの有無は混在する(ASCIIのみのエントリはフラグが立たないため)
  - **検証結果**: 5種の検体(UTF-8+フラグ / CP932フラグなし / 0x5Cトラップ / ASCIIのみ / UTF-8フラグなし)に対し、既定のUTF-8は3件、CP932固定は4件しか正しく読めず、採用方式は**5件すべて**正しく復元できた
  - **誤判定リスク**: CP932のバイト列が偶然UTF-8としても妥当になる可能性を実測した。ひらがな・カタカナ・全角記号・常用漢字の一部(計483文字)について、1文字の全数、2文字の全数(233,289通り)、3文字のランダム200万件を検査し、**衝突は0件**
  - **実装上の注意**: CP932は.NET Core以降 既定では登録されておらず、`Encoding.RegisterProvider(CodePagesEncodingProvider.Instance)` の呼び出しが必要。ただし.NET 10ではNuGetパッケージの明示的な参照は不要
  - **書き込み時**: 既定(UTF-8 + EFSフラグ)を使う。上記のカスタム `Encoding` は読み取り専用とする
- **大容量書庫でのパフォーマンス**(#14で実測、方針確定): 数万ファイル規模の書庫でもリストビューが固まらないよう、仮想化(UI Virtualization)と非同期読み込みを前提に設計する。
  - **仮想化は実装済みで有効**。30万件の一覧でも実体化される行は21件のみ。末尾へのジャンプ(Ctrl+End)は1ms、列見出しによる並べ替えは38ms、全選択は0.2秒
  - **非同期読み込みも#39で実装済み**。読み込みは別スレッドで行い、進捗と「中断」を出す。30万件の書庫を開くときにUIが応答しない最長時間は **1.2秒 → 0.29秒**。うち読み込み中の停止は18ms以下で、残りは一覧の組み立てとWPFの描画準備(UIスレッド上)
    - 中断すると、直前まで開いていた書庫の表示がそのまま残る。読み込みの失敗時も同じ
    - 中央ディレクトリの読み取り(30万件で約0.3秒)は `ZipArchive` の内部で一息に行われるため割り込めず、その間だけは中断要求が届かない
  - **文字コード判定が例外経由でCP932の書庫だけ遅かった問題は#40で解消済み**。5万件を開く時間はCP932 180ms → 69msとなり、同条件のUTF-8書庫(63ms)と並んだ。判定結果が変わらないことは1,735万件のバイト列で確認済み
  - メモリはプライベートで 180MB(空)→ 300MB(10万件)→ 420MB(30万件)
  - 起動時間は単一exeの圧縮ありで中央値524ms、圧縮なしで407ms。**71MB小さくできる対価として約110msを払っている**と評価し、圧縮は維持する
- **ウィルス検査の実現方式**(#56で実測、方式決定): Windows の AMSI(Antimalware Scan Interface)に P/Invoke し、メモリ上のバイト列を渡して判定させる。外部の対策ソフトのコマンドを呼ぶ方式は採らない。設定が要り、設定しなければ何も起きないため。
  - **実測**(Windows 11 + Defender): 初期化2〜3ms、EICARテスト検体をメモリ上のバイト列で渡すと**検出**(result=32768)、ふつうのテキストは未検出、64MBのバッファで93ms(約700MB/秒)
  - **ZIPのバイト列をそのまま渡した場合も検出**した。対策ソフト側が書庫を開いて中を見ているため、入れ子の書庫はそこに任せられる
  - EICARは規格上ファイルの先頭にある場合だけ検出される。乱数を足した検体が未検出だったのはEICARの性質であって、AMSIの限界ではない
  - **制限**: `AmsiScanBuffer` はバッファ全体を一度に渡す必要がある。大きなエントリには上限(既定256MB)を設け、超えたものは「検査できず」と報告する。黙って分割すると署名が境界で切れて見落とす
  - AMSI提供者が居ない環境では初期化に失敗する。マルウェア検査だけ「利用できません」とし、他の検査は行う
- **破損書庫・パスワード不一致時のエラーハンドリング**: ユーザーに分かりやすいエラー表示が必要。
- **AES-256暗号化ZIPの書き込みライブラリ**(フェーズ3): `System.IO.Compression`は暗号化ZIP自体に非対応。SharpCompressもAES暗号化ZIPは読み取りのみで、書き込みには7z.dllのP/Invoke(SevenZipSharp系)または自前実装が必要になる見込み。フェーズ3着手前にライブラリ調査を行い、実現方式を確定させること。
- **書庫→Explorerへのドラッグアウト**(フェーズ2、#18で方式決定): WPFからExplorerへのファイルD&Dは標準機能では完結せず、事前に一時フォルダへ展開してからの標準ファイルドロップか、遅延レンダリング(`CFSTR_FILEDESCRIPTOR`によるIDataObject実装)が必要。
  - **採用方式: 事前展開 + 標準ファイルドロップ**。`DataObject` に `FileDrop` として一時ファイルのパスを載せる。取り出し先と後片付けは「開く」(#12) の置き場をそのまま使う
  - **判断根拠**: 遅延レンダリングは COM の `IDataObject` を手書きする必要があり、ドロップ先によって要求される形式(`HGLOBAL` か `IStream` か)が変わる。得られるのは「ドラッグを取りやめた場合に展開が無駄にならない」ことと「Explorer側の進捗が出る」ことで、利用者から見た結果は変わらない。難度と得るものが釣り合わない
  - **事前展開の代償(実測)**: ドラッグの開始は同期処理のため、展開にかかる時間がそのまま無応答時間になる。**費用を決めるのはバイト数ではなくファイル数**で、1万件(各64バイト)で2.8秒、対して500MBの単一ファイルは1.5秒(展開の速度はおよそ300MB/秒、ファイル1件あたりの固定費が約0.28ms)
  - したがって**件数と合計サイズにしきい値を設け、超える場合は「展開」を使うよう促す**。しきい値を超えない範囲では0.3秒以内に収まる
  - 遅延レンダリングは将来の課題として残す

## 11. フェーズ4構想: AIによる書庫作成ルール推定と自動修正

他のアーカイバにはない差別化機能。タブ表示(フェーズ3)を前提に、複数の書庫を並べて開けることを土台にする。

### 11.1 コンセプト

一方のタブ(お手本タブ)を基準に、AIがそのフォルダ構成・命名規則などの「暗黙のルール」を推定する。もう一方のタブ(作業中タブ)に対してルール違反箇所を検出し、修正案を提示する。

### 11.2 想定ユースケース

- 過去に作った納品用書庫の構成に、新しい納品物を合わせたい
- チームで決まった書庫構成に沿っているかをAIにチェックさせたい
- 例: 「ルート直下にREADME.txtが必須」「フォルダ名は`日付_案件名`形式」「`.tmp`/`.bak`拡張子は含めない」といった規則を、明示的なルール定義なしに既存書庫から学習させる

### 11.3 大まかな処理フロー

1. お手本タブの書庫構造(フォルダ階層、ファイル名パターン、拡張子、命名規則など)をメタデータとして抽出
2. LLM APIに送信し、構造化されたルール候補を推定させる
3. 推定ルールをユーザーに提示し、確認・編集可能にする(AIの誤推定を人間が是正できることを必須とする)
4. 確定したルールを作業中タブの書庫に適用し、違反箇所をハイライト表示
5. 可能な範囲で自動修正案(リネーム、フォルダ移動、不要ファイルの除外など)を提示し、ユーザー承認の上で適用する

### 11.4 技術的検討事項

- AI/LLM APIは特定ベンダーに固定せず、**エンドポイントURLとAPIキーをユーザー自身が設定する方式**とする(設定ファイルはexeと同じフォルダに保存)
- 通信仕様(OpenAI互換/Anthropic Messages API等、どの形式に対応するか)は[10章](#10-未決事項要検討)の未決事項
- 送信する情報は**ファイル名とフォルダ構成のみ**に限定し、ファイル内容そのものは一切送信しない(確定方針)
- オフライン環境・API未設定時は機能自体を無効化する
- 誤検出時の影響を抑えるため、自動修正は必ずユーザー確認を挟み、無断上書きはしない

### 11.5 リスク・留意点

- ルール推定の精度はお手本書庫の質に依存するため、過信させないUI設計が必要(あくまで「提案」であることを明示)
- 外部API送信を伴うため、機密性の高い書庫を扱う場合は利用を避けるよう注意喚起する
- フェーズ1〜3の基本機能が安定するまでは着手しない

### 12.2 ネスト書庫(zip内zip等)を開く

将来的に対応予定。動作仕様は以下の通り確定している(実装フェーズのみ未定)。

- ネスト書庫を開くと、そのネスト書庫専用の**新しいタブ**が開かれる(親書庫のタブとは別タブとして扱う)
- ネスト書庫タブ内で変更を行った場合、その変更を**元の(親)書庫に反映するかどうかをユーザーに確認**する
- 確認のタイミングは以下の2つ:
  1. ネスト書庫のタブを閉じたとき
  2. 明示的に保存操作を行ったとき

エッジケースの挙動:

- **ネスト書庫タブが開いている状態で親書庫のタブを閉じた場合**: ネスト書庫タブは開いたまま残るが、親書庫への上書き保存(反映)は不可となる。以降は「名前を付けて保存」のみ可能とし、タブを閉じたときやアプリ終了時にも親への反映確認は行わない
- **アプリ終了時に未保存の変更があるネスト書庫タブが残っている場合**: 保存するかどうかをユーザーに確認する
