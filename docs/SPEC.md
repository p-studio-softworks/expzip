# Expzip 仕様書 v0.2

> このファイルは、開発で使っている仕様書のコピーである。正本は非公開の課題管理システムに置いてあり、
> そちらでは各機能からチケットへのリンクが張ってある。文中の `#123` はそのチケット番号。

## 1. 概要

| 項目 | 内容 |
|---|---|
| 名称 | Expzip |
| コンセプト | エクスプローラーライクなUIで書庫をブラウズ・操作できるアーカイバ |
| 配布形態 | インストール不要のポータブルアプリ(単一exe) |
| 対象OS | Windows 10/11 (x64) |
| ライセンス/利用形態 | フリーウェア(業務利用を含め完全無償)。ソースコードはMITライセンスで公開 |

## 2. フェーズ分け(スコープ管理)

| フェーズ | 内容 | 状態 |
|---|---|---|
| フェーズ1 | 書庫の閲覧・展開・追加ができるExplorerライクなブラウザ(MVP) | 対象 |
| フェーズ2 | 書庫内直接編集(インプレースでのリネーム/削除/上書き保存) | 将来(確定) |
| フェーズ3 | 7z/tar対応、パスワード付きZIP対応、タブ表示対応、多言語対応(日英)、書庫検査、ファイル分割 | 将来(確定) |
| フェーズ4 | AIによる書庫作成ルール推定と違反検出・自動修正(差別化機能) | 将来(構想、詳細は[11章](#11-フェーズ4構想-aiによる書庫作成ルール推定と自動修正)参照) |
| 保留 | シェル統合(右クリックメニュー、拡張子関連付け) | 対象外 |
| 非対応 | LZH形式(読み取りも含め非対応) | 対象外 |

判断根拠: LZHは現在ほぼ使われておらず、対応コストに見合わないため最初から除外する。シェル統合はレジストリ変更を伴い「インストール不要」の理念と相性が悪いため保留。

## 3. 対応フォーマット

| 形式 | 読み込み | 書き込み | 対応フェーズ | 備考 |
|---|---|---|---|---|
| ZIP | ○ | ○ | フェーズ1 | メイン形式 |
| ZIP(パスワード付き・AES-256) | ○ | ○ | フェーズ3(#20、実装済み) | 書き込みは AES-256 のみ |
| ZIP(パスワード付き・ZipCrypto/AES-128/192) | ○ | × | フェーズ3(#20、#67、読み取りのみ実装済み) | 読めるものはそのまま読む。作るときは AES-256 に揃える |
| 7z | ○ | × | フェーズ3(#19、読み取り実装済み) | まとめて圧縮された(ソリッド)書庫に対応。暗号化された7zは一覧のみ。書き込みは当面対応しない(#62) |
| tar / tar.gz / tar.bz2 / tar.xz | ○ | × | フェーズ3(#19、読み取り実装済み) | `.tgz` `.tbz` `.tbz2` `.txz` も同じ扱い。書き込みは当面対応しない(#62) |
| RAR | ○(将来検討) | × | 未定 | ライセンス上、自前エンコーダは実装不可。デコードのみ外部ライブラリ次第 |
| 自己解凍書庫(SFX) | ○ | × | フェーズ3(#32、読み取り実装済み) | ZIP と 7z の両方。書き換えはしない(詳細は[5.3節](#53-操作方法))。作成は[12章](#12-対応予定だがフェーズ未定の機能)参照 |
| NSIS 製インストーラー | ○ | × | フェーズ3(#68、読み取り実装済み) | 書庫ではなくインストーラーの実行ファイル。一覧と取り出しのみ(詳細は[5.3節](#53-操作方法)) |
| 書庫の中の書庫 (zip内zip等) | ○ | ○ | フェーズ3(#30、実装済み) | 専用のタブで開き、保存で親書庫へ戻す。何段でも辿れる(詳細は[5.3節](#53-操作方法)) |
| LZH | × | × | 非対応 | 明示的にスコープ外 |

MVP(フェーズ1)は **ZIPの読み書きのみ** を必須とする。

## 4. 技術スタック

- **言語/フレームワーク**: C# / .NET 10 (LTS、サポート2028年まで) + WPF
  - .NET 8はLTSサポートが2026年11月に終了するため採用しない
- **圧縮ライブラリ**:
  - ZIP: **読み取りは `System.IO.Compression`**(標準)をベースに、Shift-JISファイル名対応のためエンコーディング処理を独自にラップする。**書き換えは SharpZipLib**(#38)。`ZipArchiveMode.Update` は書庫全体をメモリに載せるため、大きな書庫では1件消すだけでも書庫の大きさぶんのメモリを使い、数GB級では失敗する
  - 7z/tar等: [SharpCompress](https://github.com/adamhathcock/sharpcompress) 0.50.4(マネージド、MIT)。ネイティブDLLを持ち込まずに済む。**単一exeは62MB→63MB、起動は524ms→546msに増えた**(#19)
  - エントリ名の文字コード判定(#13)は tar でも使う。tar は名前をそのままのバイト列で持つため、日本語圏の書庫にはCP932が入っていることがある。SharpCompress の `ArchiveEncoding.CustomDecoder` に ZIP と同じ判定器を渡している
  - パスワード付きZIP: [SharpZipLib](https://github.com/icsharpcode/SharpZipLib) 1.4.2(マネージド、MIT)。WinZip AES(128/256)と旧方式(ZipCrypto)の読み取り、AES-256 の書き込みに対応する(#20、#21で選定)
- **多言語対応**: 言語ごとの文言をC#の表として持つ(#23)。.resx とサテライトアセンブリは使わない。理由は[5.6節](#56-表示言語フェーズ323)
- **配布方式**: 発行プロファイル `src/Expzip/Properties/PublishProfiles/win-x64.pubxml` を使用する
  - `dotnet publish src/Expzip -p:PublishProfile=win-x64` で `publish/win-x64/Expzip.exe` を生成
  - 単一exeとしてビルドし、フォルダにコピーするだけで動作させる
  - トリミング(`PublishTrimmed`)はWPFでは非サポートのため使用しない
  - 代わりに単一ファイル圧縮(`EnableCompressionInSingleFile`)を有効にする。**実測で134MB → 61.8MB**まで削減できた(v0.1.0時点)
  - レジストリ書き込み・インストーラは一切使用しない

## 5. UI設計

### 5.1 基本レイアウト(Explorerライク)

フェーズ1〜2は単一書庫のみを表示する構成だった。フェーズ3でタブバーを追加し、複数書庫を並行して開けるようにした(#22。フェーズ4のAI機能は隣接タブ間の比較を前提とするため、タブ表示はその土台となる)。

```
┌─────────────────────────────────────────────┐
│ ツールバー(開く/展開/追加/パスワード/検査/分割/設定)      │
├─────────────────────────────────────────────┤
│ アドレスバー(書庫のパス + 書庫内の現在位置)         │
├─────────────────────────────────────────────┤
│ タブバー(書庫ごとに1タブ、数の上限なし)              │
├───────────────┬───────────────────────────┤
│ ツリービュー      │ リストビュー                    │
│ (書庫内フォルダ階層)│ (名前/サイズ/圧縮後/圧縮率/更新日時) │
│               │                              │
├───────────────┴───────────────────────────┤
│ ステータスバー(選択数/合計サイズ/進捗)              │
└─────────────────────────────────────────────┘
```

アドレスバーは、書庫の完全なパスから続けて書庫の中の位置までをひと続きで出す(#58)。
区切りはエクスプローラーが書庫を開いたときの表示に合わせて `\` にする。

    C:\Users\user\Desktop\資料.zip\画像\2024

書庫名だけでは同じ名前の別の書庫と区別が付かないため。長い場所はツールチップでも全体を見られるようにする。

### 5.2 タブ仕様(フェーズ3〜)

- タブ数に上限は設けない。書庫1つにつき1タブ
- 各タブはツリービューとリストビューの表示状態(**見ているフォルダ、ツリーの展開位置、選んでいた項目、並び順**)を個別に保持する
- ステータスバー・タイトルバー・アドレスバーは、現在アクティブなタブの書庫に応じて切り替わる
- **中身を出す部品はタブごとに作らず、ツリーと一覧の1組を使い回して差し替える**(#22)。部品を複製すると書庫の数だけ要素が積み上がるため。タブが持つのは「どの書庫の、どこを、どの順で見ているか」だけ
- **新しいタブで開くのは別の書庫を開いたとき**(ツールバーの「開く」、新規作成、履歴、ウィンドウへのドロップ)。既に開いている書庫を開き直そうとした場合は、そのタブへ移るだけでタブは増えない
- 読み直し(F5、書き換えのあと、外での書き換えへの追随)は、いまのタブを差し替える
- **タブの右の + で新しい書庫を作る**(#22)。エクスプローラーと同じ位置。保存先を尋ね、作った書庫を新しいタブで開く。パスワードは作成時には尋ねない(#63)。以前ツールバーにあった「新規作成」はここへ移した(同じことが2箇所にある状態を避けるため)
  - 書庫を1つも開いていない状態でもタブの帯と + は出す
  - + は TabControl の外に置く。中に置くと WPF の TabControl が中の部品を支援技術に見せないため
- 閉じ方は **タブの × / Ctrl+W / タブを中ボタンで押す** の3通り。閉じた位置の次のタブを選び、無ければ手前を選ぶ
- **Ctrl+Tab / Ctrl+Shift+Tab** で隣のタブへ移る
- 最後のタブを閉じると「書庫が開かれていません」の状態に戻る
- 読み込みや書き換えの最中はタブを閉じない。結果を差し込む先が無くなるため

### 5.3 操作方法

- 書庫を仮想フォルダとしてツリー/リストに展開表示(実ファイルシステムのように振る舞う)
- 展開の対象は、一覧で選んでいる項目。**一覧で何も選んでいない場合は、いま開いているフォルダ**が対象になる(ツリーでフォルダを選んだ状態はこれに当たる)。ルートを開いている場合は書庫全体
  - 展開先を選ぶダイアログの見出しに対象を出す(「書庫全体の展開先を選択」/「選択した項目の展開先を選択」/「「〈フォルダ名〉」の展開先を選択」)
  - **選んだものが展開先の最上位に来る**。書庫のルートからの階層は作らない。`資料/画像` を選べば展開先には `画像\…` が並ぶ。書庫全体を展開する場合はこれまでどおり階層をそのまま作る
  - 上書きの確認は、**展開先に同じ名前のファイルが実際にある場合だけ**出す。件数と名前を挙げる
  - 親へ戻る `..` の行は置かない(エクスプローラーにも無い)。一つ上へはツリーか **BackSpace** で移動する
- **NSIS 製インストーラーは中身の一覧を出し、取り出せる**(#68)
  - NSIS は書庫ではなく**インストーラーの実行ファイル**。中に取り出す手順が命令の並びとして入っていて、そのうち「ファイルを取り出す」命令 (番号20) を拾うと中身の一覧が得られる。7-Zip も同じことをしている
  - 組み立ては末尾寄りの**先頭ヘッダ** (`DEADBEEF` + `NullsoftInst`) → 直後の塊を展開 → **塊の位置表** → 命令 → 文字列表、の順。**実物で1バイトずつ突き合わせて確かめた**(展開後の大きさが記録値と一致し、命令数×28バイトが文字列表の位置と一致する)
  - 名前の中の `$INSTDIR` などの変数は符号で入っている。**番号は7ビットずつ2組**。実測で `0x809A` が 26 (`$PLUGINSDIR`)、`0x8095` が 21 (`$INSTDIR`) になり、7-Zip の出す名前と一致した
  - **取り出す命令はファイル名しか持たないことがある**。どこへ置くかは直前までの `SetOutPath` で決まるので、命令を頭から辿りながら**いまの置き場所を覚える**。追わないと階層がすべて根に並ぶ(実測: 2,991件が 2,749件に潰れた)
  - 同じファイルが複数の分岐から取り出されることがあるため、**名前と位置の組で畳む**。位置だけで畳むと、同じ中身を別の名前で置く指示を取りこぼす
  - **変数の名前は実物で確かめられた分だけ**にする。その先にも内部用の変数があるが、名前を確かめられていないので番号のまま出す。間違った名前を出すより「何番の変数か」が分かるほうがよい
  - **形式の見分けは NSIS を先に見る**。しるしが `DEADBEEF` + `NullsoftInst` と具体的なのに対し、ZIP の見分けは「末尾に終端レコードがある」だけ。NSIS の中身に ZIP が入っていると、そちらを拾って中身をまるごと取り違える(実測で確認)
  - **取り出しは塊ごとに独立している**。中身は `[4バイトの大きさ][中身]` の並びで、選んだものだけを取り出せる。判定や後始末は他の形式と揃えてある(書庫の外を指すパスを弾く、出所の印を引き継ぐ、中断したら書きかけを消す)
  - **展開後の大きさは書いていない**。一覧では「-」と出す。0 と出すと空のファイルに見えるため。圧縮後の大きさは塊の頭に書いてあるので出せる
  - **取り出した中身は 7-Zip とバイト単位で一致することを確かめてある**(273MB の実物で 32/32 件、SHA-256 で照合)
  - **まとめ圧縮 (LZMA) にも対応する**。並びが2通りあり、塊ごとの圧縮では 4バイトの大きさに続いて塊が並び、まとめ圧縮では 5バイトの LZMA の設定に続いて1本の流れになる。流れの先頭には 4バイトの長さとヘッダが入る
  - **見分けは読んでみて筋が通るかで行う**。旗には出ていないため。判定は「命令の並びの終わりが文字列表の始まりとちょうど一致するか」。読み方を間違えていれば、まず合わない
  - まとめ圧縮では**塊ごとに独立して展開できない**。位置の小さい順に並べ替え、前から順に読み飛ばしながら進む (7z と同じ性質)。塊の大きさも書庫を丸ごと展開しないと分からないため、一覧では出さない
  - **圧縮の組み合わせは4通りある**。塊ごとの 無圧縮 / Deflate / LZMA と、まとめ圧縮の LZMA。塊ごとの LZMA では、**塊の頭に5バイトの設定が入る**
  - **ANSI 版 (NSIS-2 系) にも対応する**。文字列が1バイト系で、変数の符号が `0xFC〜0xFF` になる。実物9個が手元にあり、そのうち4個で確かめた
  - **削除用のプログラム (`WriteUninstaller`) は一覧に出さない**。命令は拾えるが、そこに入っているのは素のデータで、実際の削除用プログラムはインストーラー自身と組み合わせて作られる。試しに拾うと1つの書庫で件数が合う代わりに5つで多く出てしまい、一覧の忠実さを損なった
- **自己解凍書庫 (SFX) は読み取りに対応する**(#32)。ZIP と 7z の両方
  - 自己解凍書庫は「取り出すプログラム + ふつうの書庫」を繋いだもの。**前に付いた塊を隠した流れを渡す**ことで、読む側には手を入れずに済ませている
  - ZIP は繋いだ分だけ位置がずれる。ずれ幅は終端レコードから求まる — 中央ディレクトリは終端レコードの直前で終わっているので、`(終端レコードの位置 - 中央ディレクトリの大きさ)` が本当の開始位置。**位置を書き換える道具と書き換えない道具の両方が現実にあり、どちらも開ける**
  - 7z は先頭から `7z¼¯'` のしるしを探す。書庫全体は舐めず、**頭の 4MB まで**(実物の自己解凍部は数百KBで収まる)
  - **名前が `.exe` なので、中身を見て判断する**。すべての `.exe` を書庫扱いにはしない。ドラッグ中は同じファイルの答えを覚えておき、何度も読みに行かない
  - **書き換えはしない**(読み取りのみ)。前に付いたプログラムは書庫の位置を自分の中に覚えていることがあり、書き換えると自己解凍できなくなる。壊す危険を冒す利点がない
  - 「インストーラーの中身が見える」のうち、**これに当たるのは自己解凍書庫だけ**。NSIS はまったく別の実装で、**別に作った**(#68)。PE / MSI / CAB は非対応
- **書庫の中の書庫は、専用のタブで開く**(#30)
  - 中の書庫を一時ファイルへ取り出し、それを新しいタブで開く。仕組みは「書庫内のファイルを外のアプリで開く」(#16) と同じで、**開く相手が Expzip 自身になっただけ**
  - **見分けは名前で行う**。`.exe` は中身を見ないと分からないが、対象にすると書庫でない実行ファイルまで開こうとすることになる。自己解凍書庫は取り出してから開く
  - 同じものを二度開いたときは、**取り出し直さずに開いているタブへ移る**。取り出し直すと、そのタブが見ている書庫を下から差し替えることになる
  - **入れ子は何段でも辿れる**。中の書庫のタブから、さらにその中の書庫を開ける
  - **書き換えた結果は「保存」で親の書庫へ戻す**。ツールバーの保存と Ctrl+S で、ネスト書庫のタブでだけ出す。ふだんの書き換えはその場で書庫に入るため、Expzip には保存という操作がもともと無い
  - **尋ねる時機は3つ**。保存を押したとき、タブを閉じるとき、アプリを終わるとき。書き換えるたびには尋ねない。1件足すたびに尋ねることになる
  - **書き換わったかどうかは、その場でファイルを見て決める**。書き換えたのは Expzip 自身なので、外のアプリのように見張り続ける必要がない
  - **何段でも上まで戻る**。奥を中へ戻すと中の一時ファイルが変わるので、同じ判定で中も外へ戻すことになる。終了時は内側から順に戻す
  - **親のタブが閉じられていると書き戻さない**。パスワードが要るかどうかも分からないまま書き込むことになるため。開き直してから保存し直す
  - 親のタブは次に見るときに読み直す。ただし**「外で書き換えられました」とは言わない**。書いたのは自分なので嘘になる
  - **親のタブを先に閉じた場合は、中の書庫のタブだけが残る**。以降は上書き保存ができなくなり、ボタンが「名前を付けて保存」に変わる。閉じるときも終了するときも、親への反映は尋ねない
    - 上書きしないのは、開いているタブが無いとパスワードが要るかどうかも分からないため。取り出した一時ファイルはアプリを終えると消えるので、別のファイルとして残す道だけは出しておく
    - 親のタブを閉じた時点で、そうなったことをステータスバーに出す。押せる操作が黙って変わると、書いたものが戻らない理由が分からない
  - **書き戻す先のパスワードは、書き戻す先の書庫から引く**。以前は「いま見ているタブ」から引いていて、開いたときと違うタブを見ている状態で保存されると取り違えた (#16 から潜んでいた)
  - **タブの名前を支援技術に伝える**。既定では型名がそのまま読み上げられ、どの書庫のタブか分からなかった
- **読み込みは ZIP の圧縮方式と鍵長をひととおり通す**(#66、#67)。7-Zip などが作る **LZMA / PPMd / BZip2 / Deflate64** も、**AES-128 / AES-192 / AES-256 / 旧方式 (ZipCrypto)** も、展開・検査ともに扱える
  - **AES-192 は SharpZipLib が鍵長 24 バイトを受け付けない**(#67)。しかも投げるのが素の `Exception` で、型で並べた `catch` をすり抜けて処理ごと落ちていた。開き直す道に載せて解決した
  - **実際に出回る形を15種類作って通してある**(#67): ZIP64 (7万件 / 拡張領域つき)、データ記述子、暗号化4種、空フォルダ、コメント、0バイト、406文字のパス、同名2件、区切りが円記号、Unix属性、SFX の形。**すべて通る**(SFX の形も #32 で読めるようになった)
  - 標準の `System.IO.Compression` が復号できるのは**格納・Deflate・Deflate64 の3つだけ**。SharpZipLib は代わりに BZip2 を扱えるが Deflate64 を扱えない。**どちらか一方では足りない**
  - そこで、**標準の実装で開けなかったエントリだけ SharpCompress に回す**。ふだんの ZIP の道筋は変えない。書き換えは「一部の差し替え」で作り込んであり (#38)、文字コード判定 (#13) や出所の印の扱いも標準側に寄せてあるため
  - **検査 (#53) も同じ道を通す**。以前は読めない方式を「取り出せない」として**危険**と判定していた。正しい書庫を危険と呼ぶのは誤りで、いまは開き直して CRC まで確かめる
  - SharpCompress は方式ごとに独自の例外を投げるため、**境目で読み取りの失敗を1つの型に揃える**。型を並べて追いかけると、新しい方式が増えるたびに拾い漏れて画面ごと落ちる
  - **読めなかったエントリの書きかけは消す**。中身が途中までのファイルは、見た目が正常なだけに何も残らないより悪い
- **圧縮するかどうかはファイルごとに自動で決める**(#38)。利用者には選ばせない
  - 先頭の64KBを試しに圧縮してみて、**3%も縮まないなら格納する**。拡張子の表では決めない(中身が名前どおりとは限らず、表は増え続けるうえ知らない拡張子を外すため)
  - **実測**(#38): 既に圧縮されているもの(JPEG、MP4、ZIP など)は deflate をかけても**1バイトも縮まず**、時間だけ 8.5倍かかる。64MBで 格納185ms 対 圧縮1,567ms。逆にログは 99.7%縮み、実行ファイルは 54.3%縮む
  - **書庫全体に一律で掛ける設定にはしない**。写真とログが混ざったフォルダでは必ずどちらかが損をするため。7-Zip と同じ考え方
  - パスワード付き書庫では、残すエントリは元の書庫での扱いを引き継ぐ
- **開いている書庫が外で書き換えられたら、尋ねずに読み直す**(#64)。**ツールバーに更新ボタンは置かない**
  - 尋ねずに読み直すのは、一覧を最新にするだけで失うものが無いため。古い一覧のままだと、無いファイルを開こうとしたり、消えたはずのファイルを取り出したりしてしまう
  - 手で読み直す道は **F5 と右クリックメニューの「最新の情報に更新」** に残す。文言はエクスプローラーに合わせる
  - 変更の検出は編集中のファイル (#16) と同じ仕掛けで、**更新日時と大きさの組を1秒ごとに見る**。別名で書いてから置き換える作法でも拾えるため、ファイル監視ではなくパスを見に行く
  - **2回続けて同じ状態が見えたときだけ読み直す**。書き込みの途中で読むと壊れた書庫にしか見えないため。大きな書庫の書き換えは数秒かかる
  - **読めなかったときは黙って今の一覧を残す**。頼んでいない読み直しでダイアログを出さない。知らせはステータスバーに出し、同じ書き換えで毎秒やり直さない
  - **見ていないタブは印だけ付け、そのタブへ移ったときに読み直す**。裏で読み直すと、見ている書庫の表示が別の書庫の読み込みで置き換わるため
  - **ファイルを見に行くのは別スレッド**。ネットワーク上の書庫では状態を1つ読むだけでも待たされることがあり、画面を動かす筋で読むと窓が固まる(#39)
  - 自分で書き換えたあとは必ず読み直しており、そこで控えを取り直すので巡回は何も見つけない
- リストビューの列ヘッダクリックでソート
- ダブルクリックでフォルダ移動 / ファイルは一時展開して既定アプリで開く(Enter キーおよび右クリックメニューの「開く」も同じ動作)
  - 一時展開先は `%TEMP%\Expzip\session-*`。exe と同じフォルダには置かない(持ち運び先が書き込み不可のことがあるため)
  - 一時展開したファイルはアプリ終了時に削除する。開いたままのアプリに掴まれていて削除できなかった分は、次回起動時に片付ける
  - 一時展開したファイルは読み取り専用にしない
  - **開いた先で保存されたら、書庫へ反映するか尋ねる**。「開く」と「編集」を分けない。どちらも既定のアプリに渡すだけで見た目が同じになり、違いが伝わらないため
    - 変更の検出は更新日時と大きさの組を1秒ごとに見る方式。保存の作法(その場で書き換える / 別名で書いてから置き換える)がアプリによって違い、後者では対象のファイルが一度消えて作り直されるため、ファイル監視ではなくパスを見に行く
    - 反映を「いいえ」で見送った変更は、**アプリ終了時に改めて尋ねる**。そこで「いいえ」を選ぶと変更は失われる
    - 反映せずに終わった場合、一時展開したファイルは終了時に消える
  - 実行されうる拡張子(`.exe` `.bat` `.vbs` `.lnk` など)は開く前に確認する。既定は「キャンセル」
  - 書庫に出所の印(Mark of the Web)が付いている場合は、書き出したファイルにも引き継ぐ。SmartScreen や保護ビューが働かなくなるのを防ぐため。一時展開だけでなく、**「展開」とドラッグアウトでも引き継ぐ**
- 名前の変更(F2 または右クリックメニュー)。**一覧の上でその場で書き換える**(エクスプローラー と同じ。ダイアログは出さない)。ファイルとフォルダの両方に対応し、フォルダは配下ごと付け替える
  - 開始は **F2 / 右クリックメニュー / 選択済みの項目の名前をもう一度クリック** の3通り(エクスプローラー と同じ)
    - クリックで始めるものは、ダブルクリックの2回目が来ないことを確かめてから始める。開くつもりの操作で入力欄が出ないようにするため。待つ長さは利用者の設定 (`GetDoubleClickTime`) に従う
    - 名前の列を押した場合だけ。サイズなど他の列を押しても始まらない
  - 拡張子を除いた部分だけを選んだ状態で始まる。Enter で確定、Esc で取り消し
  - **入力欄の外を押した時点で確定する**。一覧の余白など、フォーカスの移らない場所を押した場合も終わる
  - 同じフォルダに同名の項目がある場合、`\` `/` を含む場合、展開先で作れない文字を含む場合は変更しない
  - ZIPにはエントリ名だけを書き換える手段が無いため、**名前を変えた項目は圧縮し直される**。中身は変わらないが圧縮後のサイズは変わりうる。対象外の項目はそのまま持ち越す
- **書庫内での移動**。項目を掴んで、ツリーのフォルダまたは一覧のフォルダへ落とす
  - フォルダは配下ごと動く。複数まとめて動かせる
  - 移動先に同じ名前がある場合、元と同じ場所へ落とした場合、自分自身や自分の配下へ落とした場合は受け付けない
  - 名前の変更と同じ仕組みで、**動かした項目は圧縮し直される**
  - 外へ落とせば取り出し、中へ落とせば移動になる。ドラッグには書庫内の情報も載せてあり、Explorer はそれを無視して通常のファイルとして受け取る
- ドラッグ&ドロップ:
  - Explorer→書庫へのファイル追加: フェーズ1
  - 書庫→Explorerへのドラッグアウト(展開): 一時フォルダへ取り出してから標準のファイルドロップとして渡す(方式の選定は[7章](#7-既知の技術的リスク)参照)
    - 取り出し先と後片付けは「開く」と同じ置き場を使う
    - **ツリービューのフォルダも掴んで出せる**。ルート(書庫そのもの)を掴んだ場合は直下の項目をまとめて渡す
    - ドラッグの開始は同期処理で途中に進捗を挟めないため、**3,000件 / 512MB を超える選択では「展開」を使うよう促す**
    - 取り出したファイルは読み取り専用にしない。ドロップ先にそのままコピーされるため
- **ウィンドウに書庫を1つ落とすと、その書庫を開く**
  - 書庫を開いていない状態でも受け取る
  - 「落としたら開く」と「落としたら中に入れる」は両立しないため、開くほうを既定にする。**書庫を書庫の中に入れたい場合は Shift を押しながら落とす**。使う頻度は開くほうが高いという判断
  - 書庫以外、または複数のファイルを落とした場合は、これまでどおり追加する
  - 一覧の上だけでなく、ツリーやステータスバーの上に落としても受け取る
- **書庫の中に空のフォルダを作る**(右クリックメニューの「新しいフォルダ」または Ctrl+Shift+N)
  - 作る場所はいま開いているフォルダ。ツリーの節を右クリックした場合は、その節へ移ってから作る
  - 名前を尋ねるダイアログは出さず、`新しいフォルダー` として作ってその場で書き換えられる状態にする(エクスプローラーと同じ)。既にあれば `新しいフォルダー (2)` のように番号を付ける
  - ZIPはフォルダを明示的に持たなくてもよく、中身のあるフォルダはファイルのパスから組み立てられる。空のフォルダはそれでは表せないため、末尾が `/` のエントリを1件書き込む
- **パスワード付きZIP**(#20)
  - 一覧は合言葉なしで読める(エントリ名は暗号化されないため)。**中身を取り出すときに尋ねる**
  - 一度入れた合言葉は、**そのタブを閉じるまで**覚えておく。閉じたら忘れ、開き直せば改めて尋ねる。設定ファイルには書かない
  - 合っているかを取り出す前に確かめる。違う合言葉で始めると、中身が壊れたファイルが書き出されるため
  - **保護された項目は名前を緑 (`#107C10`) で出す**。保護されていることは色で示す。緑にするのは、エクスプローラーが EFS で暗号化されたファイルを緑で出す習わしに倣ったもの。**色そのものは合わせていない**(あちらの既定は `#008000` あたりの深緑)。白地で読みやすいほうを採った
    - ZIP も 7z もエントリごとに暗号化できるため、印は**エントリごと**に付ける。フォルダは中身から決め、配下に保護されたファイルがあれば色を変える
    - **選ばれている行の地は、ツリーも一覧も薄い青にする**(#65)。WPF の既定ではツリーの節だけ `SystemColors.Highlight` の濃い青 (`#0078D4`) になり、緑との明暗差が **1.19 : 1** まで落ちて文字が沈む。同じ窓の中で選択の見え方が2種類あるのも紛らわしい。一覧が使う Aero の薄い青に揃えると **4.48 : 1** になる。エクスプローラーも薄い青地で文字色を変えない
    - 色だけに頼らないよう、保護された項目にはツールチップも添える
    - どのエントリが保護されているかを名前で引き当てるのは、**一部だけが暗号化された書庫のときだけ**。まるごと暗号化されている書庫でエントリ名をもう一組抱えるのを避ける(30万件で中央ディレクトリの走査は約350ms)
  - **書庫を作るときには尋ねない**(#63)。付ける・変える・外すは、ツールバーの**「パスワード」**から行う
    - 付いていない書庫では、付けるパスワードを尋ねる。中身のある書庫なら、既にあるエントリも AES-256 で暗号化し直す
    - 付いている書庫では、新しいパスワードを尋ねる。**空のままにすると外す**
    - 中身が無い書庫では合言葉を覚えるだけ。最初に何かを入れるときから暗号化する
    - パスワードを扱えるのは ZIP のみ。7z / tar では押せない
  - パスワード付きの書庫も書き換えられる。ただし**書庫全体を作り直す**(残すエントリも復号して暗号化し直す)。書き換えの間はその旨を出す
  - 読めるのは AES(128/192/256)と旧方式(ZipCrypto)(#67)。**作るときは AES-256 に揃える**
- 右クリックコンテキストメニュー(アプリ内のみ。OSシェルへの統合はしない)
  - 一覧: 開く / 名前の変更 / 削除 / 新しいフォルダ。項目の上でも、何もない場所でも出る
  - ツリー: 新しいフォルダ

### 5.4 書庫検査(フェーズ3、#53)

ツールバーの「検査」から、開いている書庫をまとめて調べて1枚の報告にする。検査の種類ごとにメニューを分けない。利用者が知りたいのは「この書庫は安全に開けるか」の一点で、種類の区別は実装側の都合のため。

- **起動は手動のみ**。書庫を開くたびには走らせない(開く速さを損なうため)。開いた時点で出す「パスが通常ではない項目」の警告(#36)はこれまでどおり
- **見るもの**
  - 構造(#54): CRCの照合(全エントリを実際に展開して確認)、中央ディレクトリとローカルヘッダの食い違い、切り詰められた書庫、末尾の余分なデータ、未対応の圧縮方式、重複するエントリ名
  - 安全性(#55): 書庫の外を指すパス、Windowsで作れない名前(`CON` `PRN`、末尾の空白やピリオド、制御文字、`:` などの記号)、大文字小文字だけ違う衝突、右横書き記号(U+202E)による拡張子の偽装、圧縮率が異常なエントリ(ZIP爆弾)、実行されうる拡張子
  - マルウェア(#56): AMSI に各エントリの中身を渡す。書庫ファイル自身も渡し、入れ子の書庫は対策ソフト側に開いてもらう
- **結果**(#57): 「重大度 / 対象 / 内容」の一覧。行を選ぶとその項目へ飛ぶ。**問題が無かったことも明示する**(何も出ないと検査が働いたのか分からないため)
- **駆除・隔離・削除はしない**。報告して終わりにする。書庫の中身をどうするかは利用者が決めること
- CRC照合は書庫を丸ごと読むため、進捗と中断に対応する(#39 の仕組みに載せる)

実装で決めたこと。

- **CRCの照合とマルウェア検査は、1度の読み出しに相乗りさせる**。どちらも「エントリの中身そのもの」を必要とするため、別々に行うと書庫を二度読むことになる。索引とヘッダの照合だけは中身を読まずに済むので先に行う
- **報告の中身は文言ではなく事柄の種類で持つ**。表示するときに `Strings` を通すので、検査が済んだあとに言語を切り替えても報告の文字が入れ替わる(#23)
- **同じ種類は200件まで並べ、残りは「ほかに N 件」の1行にまとめる**。すべてのファイルが実行形式、といった書庫では、そのまま並べると重い事柄が埋もれる。数え上げには省いた分も入れる
- **報告の頭に出すのは結末だけにする**。「何をどれだけ調べたか」は変わるのが数だけで、利用者が知りたいのは結果そのもの。「調べた内容」として畳んでおき、見たい人が開けるようにする。**マルウェア検査が使えなかったことだけは畳まない**(結果そのものの意味が変わるため)
- **パスワード付きの書庫では、始める前に合言葉を尋ねる**。断られても検査は続け、中身を見られなかった項目は「調べられなかった」として報告する。名前や索引で分かることは合言葉なしでも調べられるため
- **AMSI が使えない環境では、マルウェア検査だけを見送る**。使えなかったことは報告にはっきり出し、黙って省かない
- **進み具合は「1件あたり0.5MB相当」の見積もりで測る**。読んだバイト数だけで測ると、小さなファイルが何万件も入った書庫では表示がほとんど動かない。経過の間引き(0.1秒に1回)は通知の口で受け止め、検査ごとには書かない
- **費用はほぼ AMSI の呼び出し回数で決まる**(実測)。1件あたり0.7〜4ms、書庫を読むこと自体は2,000件で24〜157ms。10,000件で7秒、50,000件で35秒、300,000件で4分。手で押したときだけ走り、進捗と中断が付いているため、この費用は受け入れる
- 検査で使う判定のうち、パスの安全性は `ArchivePath`(#36)、実行されうる拡張子は `RiskyFileTypes`(#12)を再利用する。同じ現象を2か所で別々に判定すると食い違う

### 5.5 ファイルの分割(フェーズ3、#59)

大きなファイルを決まった大きさに分割し、あわせて連結用のプログラムを作る。

- **設定は3つだけ**にする。対象のファイル(既定はいま開いている書庫、参照で任意のファイルも選べる)、分割先フォルダ(既定は元と同じ場所)、分割サイズ(数値と KB / MB / GB。下限128KB、上限なし)
- 元のファイルより大きい分割サイズが指定されたら「分割の必要はありません」と出す
- **連結方法は選ばせない**。常に Win32 用の自己連結プログラムを**別個に**作り、**CRCチェックを有効**にする。連結用のバッチファイルは非対応
- 断片は `<元の名前>.001` `.002` … とする。7-Zip と同じ形式で、他のソフトでも連結できる。連結プログラムは `<元の名前>.exe`
- 進捗と中断を出す。元のファイルは消さない
- 分割先のリムーバブルメディアの容量から大きさを決める機能は持たない
- **押す前に何個になるかを出す**。分割の必要が無い場合もその場で分かる
- 中断したら書きかけの断片は消す。中途半端なものを残すと「揃っている」と勘違いさせるため

**連結プログラムの作り方**(#60で実測、方式決定): **C ランタイムを使わない C の Win32 プログラムを x86 で建て、出来上がりをリポジトリに同梱する**。

| 案 | 出来上がり | 建てるのに要るもの |
|---|---|---|
| **C / C ランタイム無し(採用)** | **4,608 バイト** | MSVC |
| .NET NativeAOT(x86) | 747,520 バイト | MSVC(ILCompiler が link.exe を呼ぶ) |
| .NET NativeAOT(x64) | 881,152 バイト | MSVC |
| PE を自前で組み立てる | 最小 | なし |

- NativeAOT でも結局 MSVC が要るため、**「C を持ち込まない」という利点が無い**。そのうえ 160 倍大きい。PE を自前で書き出す案は壊れやすく保守できないため採らない
- **Expzip 本体を建てるのに C のツールチェーンは要らない**。出来上がり(4.6KB)を `src/Expzip/Resources/joiner-x86.exe` として同梱し、`dotnet build` だけで通るようにしてある。ソースと建て直し方は `tools/joiner` にある
- **x86 で建てる**。32bit と 64bit のどちらの Windows でも動くため
- 元の名前・断片の数・大きさ・CRC は、実行ファイルの**末尾に書き足す**。形は `tools/joiner/README.md` にある
- **対策ソフトの誤検知は出なかった**(Defender で実測。出所の印を付けた場合も同じ)。ただし**署名していないため、受け取った人の環境では SmartScreen が警告することがある**。断片そのものは 7-Zip などでもつなげる形にしてあるので、連結プログラムが使えなくても行き止まりにはならない

### 5.6 表示言語(フェーズ3、#23)

日本語と英語を切り替えられるようにする。フェーズ1〜2は日本語のみだった。

- 既定は **OS の表示言語に合わせる**。Windows の表示言語が日本語なら日本語、それ以外はすべて英語
- ツールバー右端の **歯車 → 言語** で `OS に合わせる` / `日本語` / `English` を選ぶ。選んだ内容は設定ファイルの `Language`(`auto` / `ja` / `en`)に残る
- 切り替えは**その場で反映する**。再起動は要らない。開いている書庫やタブ、選択、並び順はそのまま
- 処理の最中に切り替えた場合、進行中の経過表示だけは書き換えない。次に何か表示した時点で切り替わる
- **文言は `Localization/Strings.cs` の表に日本語と英語を並べて持つ**。.resx とサテライトアセンブリは使わない
  - 単一exeで配布するため(3章)。サテライトを増やすと発行物がexe1つでなくなる
  - 片方だけ書くことが文法上できないため、訳の抜けが起きない
  - 件数や名前を差し込む文言をメソッドで書けるため、語順や英語の複数形を素直に扱える(`1 file` / `2 files`)
  - 3言語を超える場合はこの形が割に合わなくなる。そのときは .resx へ移す
- **XAML には文言を書かない**。起動時と切り替え時に `MainWindow.ApplyLanguage` がまとめて入れる。入れ忘れた部品は空欄になってすぐ分かる
- 並び順は**列見出しの文字ではなく列そのもの**で覚える(`EntryColumn`)。文字で持つと言語を切り替えた瞬間に並び順を見失うため
- 数値と日付の書式は OS の地域設定のまま。表示言語だけを切り替え、`CurrentCulture` は変えない
- 絵文字だけのボタン(履歴、設定、新しい書庫)には、支援技術向けの名前を言語に合わせて付ける

## 7. 既知の技術的リスク

- **文字コード問題**(#13で検証済み、方式決定): ZIP仕様上、ファイル名のエンコーディングは一意に定まらない。EFSフラグ(汎用フラグbit11)が立つエントリはUTF-8だが、立たないエントリは本来CP437であり、日本語圏の既存ツールはそこにCP932を書いてきた。日本語の書庫を扱うアーカイバでは、この判別精度が使い勝手を大きく左右するので、妥協できない箇所。
  - **採用方式**: `ZipArchive` の `entryNameEncoding` にカスタム `Encoding` を渡し、フラグなしエントリを「UTF-8として厳密に妥当ならUTF-8、そうでなければCP932」と判定する。フラグ付きエントリは.NETが常にUTF-8として扱うため干渉しない
  - **判定はエントリ単位**で行う。同一書庫内でもフラグの有無は混在する(ASCIIのみのエントリはフラグが立たないため)
  - **検証結果**: 5種の検体(UTF-8+フラグ / CP932フラグなし / 0x5Cトラップ / ASCIIのみ / UTF-8フラグなし)に対し、既定のUTF-8は3件、CP932固定は4件しか正しく読めず、採用方式は**5件すべて**正しく復元できた
  - **誤判定リスク**: CP932のバイト列が偶然UTF-8としても妥当になる可能性を実測した。ひらがな・カタカナ・全角記号・常用漢字の一部(計483文字)について、1文字の全数、2文字の全数(233,289通り)、3文字のランダム200万件を検査し、**衝突は0件**
  - **実装上の注意**: CP932は.NET Core以降 既定では登録されておらず、`Encoding.RegisterProvider(CodePagesEncodingProvider.Instance)` の呼び出しが必要。ただし.NET 10ではNuGetパッケージの明示的な参照は不要
  - **書き込み時**: 既定(UTF-8 + EFSフラグ)を使う。上記のカスタム `Encoding` は読み取り専用とする
- **大容量書庫でのパフォーマンス**(#14で実測、方針確定): 数万ファイル規模の書庫でもリストビューが固まらないよう、仮想化(UI Virtualization)と非同期読み込みを前提に設計する。
  - **仮想化は実装済みで有効**。30万件の一覧でも実体化される行は21件のみ。末尾へのジャンプ(Ctrl+End)は1ms、列見出しによる並べ替えは38ms、全選択は0.2秒
  - **非同期読み込みも#39で実装済み**。読み込みは別スレッドで行い、進捗と「中断」を出す。30万件の書庫を開くときにUIが応答しない最長時間は **1.2秒 → 0.29秒**。うち読み込み中の停止は18ms以下で、残りは一覧の組み立てとWPFの描画準備(UIスレッド上)
    - 中断すると、直前まで開いていた書庫の表示がそのまま残る。読み込みの失敗時も同じ
    - 中央ディレクトリの読み取り(30万件で約0.3秒)は `ZipArchive` の内部で一息に行われるため割り込めず、その間だけは中断要求が届かない
  - **文字コード判定が例外経由でCP932の書庫だけ遅かった問題は#40で解消済み**。5万件を開く時間はCP932 180ms → 69msとなり、同条件のUTF-8書庫(63ms)と並んだ。判定結果が変わらないことは1,735万件のバイト列で確認済み
  - メモリはプライベートで 180MB(空)→ 300MB(10万件)→ 420MB(30万件)
  - 起動時間は単一exeの圧縮ありで中央値524ms、圧縮なしで407ms。**71MB小さくできる対価として約110msを払っている**と評価し、圧縮は維持する
- **ウィルス検査の実現方式**(#56で実測、方式決定): Windows の AMSI(Antimalware Scan Interface)に P/Invoke し、メモリ上のバイト列を渡して判定させる。外部の対策ソフトのコマンドを呼ぶ方式は採らない。設定が要り、設定しなければ何も起きないため。
  - **実測**(Windows 11 + Defender): 初期化2〜3ms、EICARテスト検体をメモリ上のバイト列で渡すと**検出**(result=32768)、ふつうのテキストは未検出、64MBのバッファで93ms(約700MB/秒)
  - **ZIPのバイト列をそのまま渡した場合も検出**した。対策ソフト側が書庫を開いて中を見ているため、入れ子の書庫はそこに任せられる
  - EICARは規格上ファイルの先頭にある場合だけ検出される。乱数を足した検体が未検出だったのはEICARの性質であって、AMSIの限界ではない
  - **制限**: `AmsiScanBuffer` はバッファ全体を一度に渡す必要がある。大きなエントリには上限(既定256MB)を設け、超えたものは「検査できず」と報告する。黙って分割すると署名が境界で切れて見落とす
  - **AMSI は Windows の口であって Defender のものではない**。Defender の代わりに別の対策ソフトを入れている環境でも、その製品が提供者として登録していれば同じように働く。Expzip 側は製品名を知らないし、知る必要もない
  - **提供者が1つも登録されていなければ、マルウェア検査だけ「利用できません」とし、他の検査は行う**。判定は `HKLM\SOFTWARE\Microsoft\AMSI\Providers` に登録があるかで行う。初期化に成功しただけでは判定が働いているとは言えず、応じる相手が居なければ問い合わせはいつも「問題なし」で返るため
  - **試験検体 (EICAR) を1つ通して確かめる方法は採らない**。確実ではあるが、対策ソフトの検出履歴に「Expzip.exe で脅威を検出」として毎回残る(Defender で実測)。利用者から見れば Expzip 自身がマルウェアに見えてしまう
  - **登録があっても、その製品が実際に答えるとは限らない**(別の対策ソフトを入れると Defender は待機側に回る)。そこまでは見分けられないため、報告では「安全です」とは言わず「判定に掛けました」と書く
  - **費用を決めるのは呼び出し回数**(#53で実測)。1件あたり0.7〜4ms(中身の大きさではなく件数で効く)。書庫を読むこと自体は2,000件で24〜157msにすぎず、検査の時間はほぼ AMSI が占める。10,000件で7秒、50,000件で35秒、300,000件で4分
  - **分割して渡さない**という制限があるため、まとめて速くする手がない。手で押したときだけ走らせ、進捗と中断を付けることで受け入れる
- **7zはまとめて圧縮されている(ソリッド)**(#19で実測、方式決定): エントリを1件ずつ開くと、そのたびに同じ塊を復号し直すことになる。
  - **実測**(2,000件・740KBの7z): 1件ずつ開く方式で**50.4秒**、先頭から順に読む方式(`ExtractAllEntries`)で**0.14秒**。**370倍**の差
  - したがって**2件以上を取り出すときは必ず順に読む**。1件だけのときは、その塊を復号するだけで済むので直接開く
  - 形式ごとの費用(2,000件、書庫を開く/全部展開): ZIP 1ms/553ms、7z 3ms/591ms、tar 12ms/526ms、tar.gz 62ms/537ms。tar.gz を開くのに時間がかかるのは、一覧を作るだけでも全体を伸長する必要があるため(tarは中央の索引を持たない)
  - 7z はエントリごとの圧縮後サイズを持たない。一覧では「-」と出し、0として出さない(「まったく場所を取っていない」ように見えるため)
- **7z / tar の書き込み**(#62で調査、**当面は対応しない**): SharpCompress は 7z (LZMA / LZMA2) と tar を書ける。実際に書き出し、同梱の 7-Zip 25.01 に検めさせて3形式とも通った。依存は1つも増えない。それでも読み取りのみに揃える
  - **書き込み口が流し書きしかない**(`WriterFactory.OpenWriter`)。空の書庫を作って後から足すことができない。Expzip の新規作成は「空の書庫を作ってから足していく」形なので、7z では「選んだファイルを一度にまとめて書き出す」という**二つ目の作り方**を画面に足すことになる。「新規作成」が形式によって別物になるのは、使う側から見て分かりにくい
  - **数の裏付け**: この PC の書庫435個のうち 7z は2個、tar は31個。ZIP 系が386個で89%を占める
  - **[9章](#9-明示的にスコープ外とする項目全フェーズを通じて非対応)には入れない**。できないのではなく、いまは割に合わないという判断のため。7z を扱う機会が増えたときや、「まとめて 7z にする」用途が要るようになったときに見直す

- **AES-256暗号化ZIPの書き込み**(#21で調査、方式決定): SharpZipLib(MIT、純マネージド)を採用した。`ZipOutputStream` に合言葉と `AESKeySize = 256` を渡すだけで WinZip AES として書ける。
  - **相互運用を確認済み**: Expzip が書いたものを別実装(Python の pyzipper)が読め、pyzipper が書いたものを Expzip が読める
  - `System.IO.Compression` は暗号化ZIPの一覧は読めるが中身は読めない(AESのエントリは圧縮方式99として記録されるため「対応していない圧縮方式」になる)
  - **暗号化の判定は書庫を開くたびに行う**。「開いてみて駄目なら暗号化」では旧方式(ZipCrypto)を見逃す。あちらは圧縮方式が変わらないため開けてしまい、復号されない中身がそのまま出てくる。代償として書庫を開く時間が伸びた(30万件で 290ms → **740ms**)
  - **既にある書庫へ暗号化したエントリを足すことはできない**(SharpZipLib の制限。「Creation of AES encrypted entries is not supported」)。そのため追加・削除・名前の変更・移動はすべて**書庫全体の作り直し**になる
  - **実測**(2,000件): 書庫を作るのは 暗号化なし948ms / パスワード付き2,006ms。**そこへ1件足すのは 28ms / 3,457ms(123倍)**。暗号化そのものは速く(10MBで約10ms)、費用は作り直しに由来する
- **大きな書庫の書き換えでメモリを使いすぎる**(#38で実測、方式決定): `ZipArchiveMode.Update` は**書庫全体をメモリに載せる**。**書き換えは SharpZipLib に寄せた**。
  - **実測**(800MBの書庫から1件消す): `System.IO.Compression` は ヒープ 0MB → **800MB** / 672ms、SharpZipLib は 0MB → **1MB** / 1,603ms。約2.4倍遅いが、メモリは 800分の1で済み、数GB級でも動く
  - **追加だけの問題ではなかった**。削除・名前の変更・移動・フォルダ作成も同じく書庫の大きさぶんのメモリを使っていた
  - **変えないエントリは圧縮し直さない**。SharpZipLib は圧縮済みのデータをそのまま写す。300件の書庫に1件足しても、元の300件は圧縮後サイズもCRCも変わらないことを確認済み
  - **1操作の費用は書庫の大きさに比例する**(再圧縮ではなく写しのため)。50MB=204ms、200MB=343ms、800MB=1,273ms でおよそ600MB/秒。10回の追加をまとめると 424ms → 50ms
  - **中断は読み取り側で投げる**。中身が読まれるのは `CommitUpdate` の最中で割り込む口が無いため、供給元のストリームが中断を投げて書き換えを取りやめる。元の書庫はバイト単位でそのまま残る
  - **圧縮するかどうかは利用者に選ばせず、ファイルごとに自動で決める**。書庫全体に一律で掛ける設定にすると、写真とログが混ざったフォルダでは必ずどちらかが損をするため。7-Zip と同じ考え方。詳細は[5.3節](#53-操作方法)
- **破損書庫・パスワード不一致時のエラーハンドリング**: ユーザーに分かりやすいエラー表示が必要。
- **書庫→Explorerへのドラッグアウト**(フェーズ2、#18で方式決定): WPFからExplorerへのファイルD&Dは標準機能では完結せず、事前に一時フォルダへ展開してからの標準ファイルドロップか、遅延レンダリング(`CFSTR_FILEDESCRIPTOR`によるIDataObject実装)が必要。
  - **採用方式: 事前展開 + 標準ファイルドロップ**。`DataObject` に `FileDrop` として一時ファイルのパスを載せる。取り出し先と後片付けは「開く」(#12) の置き場をそのまま使う
  - **判断根拠**: 遅延レンダリングは COM の `IDataObject` を手書きする必要があり、ドロップ先によって要求される形式(`HGLOBAL` か `IStream` か)が変わる。得られるのは「ドラッグを取りやめた場合に展開が無駄にならない」ことと「Explorer側の進捗が出る」ことで、利用者から見た結果は変わらない。難度と得るものが釣り合わない
  - **事前展開の代償(実測)**: ドラッグの開始は同期処理のため、展開にかかる時間がそのまま無応答時間になる。**費用を決めるのはバイト数ではなくファイル数**で、1万件(各64バイト)で2.8秒、対して500MBの単一ファイルは1.5秒(展開の速度はおよそ300MB/秒、ファイル1件あたりの固定費が約0.28ms)
  - したがって**件数と合計サイズにしきい値を設け、超える場合は「展開」を使うよう促す**。しきい値を超えない範囲では0.3秒以内に収まる
  - 遅延レンダリングは将来の課題として残す

## 11. フェーズ4構想: AIによる書庫作成ルール推定と自動修正

他のアーカイバにはない差別化機能。タブ表示(フェーズ3)を前提に、複数の書庫を並べて開けることを土台にする。

### 11.1 コンセプト

一方のタブ(お手本タブ)を基準に、AIがそのフォルダ構成・命名規則などの「暗黙のルール」を推定する。もう一方のタブ(作業中タブ)に対してルール違反箇所を検出し、修正案を提示する。

### 11.2 想定ユースケース

- 過去に作った納品用書庫の構成に、新しい納品物を合わせたい
- チームで決まった書庫構成に沿っているかをAIにチェックさせたい
- 例: 「ルート直下にREADME.txtが必須」「フォルダ名は`日付_案件名`形式」「`.tmp`/`.bak`拡張子は含めない」といった規則を、明示的なルール定義なしに既存書庫から学習させる

### 11.3 大まかな処理フロー

1. お手本タブの書庫構造(フォルダ階層、ファイル名パターン、拡張子、命名規則など)をメタデータとして抽出
2. LLM APIに送信し、構造化されたルール候補を推定させる
3. 推定ルールをユーザーに提示し、確認・編集可能にする(AIの誤推定を人間が是正できることを必須とする)
4. 確定したルールを作業中タブの書庫に適用し、違反箇所をハイライト表示
5. 可能な範囲で自動修正案(リネーム、フォルダ移動、不要ファイルの除外など)を提示し、ユーザー承認の上で適用する

### 11.4 技術的検討事項

- AI/LLM APIは特定ベンダーに固定せず、**エンドポイントURLとAPIキーをユーザー自身が設定する方式**とする(設定ファイルはexeと同じフォルダに保存)
- 通信仕様(OpenAI互換/Anthropic Messages API等、どの形式に対応するか)は[10章](#10-未決事項要検討)の未決事項
- 送信する情報は**ファイル名とフォルダ構成のみ**に限定し、ファイル内容そのものは一切送信しない(確定方針)
- オフライン環境・API未設定時は機能自体を無効化する
- 誤検出時の影響を抑えるため、自動修正は必ずユーザー確認を挟み、無断上書きはしない

### 11.5 リスク・留意点

- ルール推定の精度はお手本書庫の質に依存するため、過信させないUI設計が必要(あくまで「提案」であることを明示)
- 外部API送信を伴うため、機密性の高い書庫を扱う場合は利用を避けるよう注意喚起する
- フェーズ1〜3の基本機能が安定するまでは着手しない
