# リリース

手順の正本は、課題管理の Wiki「リリースの手順」と「Microsoft_Store_の掲載情報」にある。ここに手順を書き写さないので、始める前に `redmine` スキルで両方を読み、上から順に進める。

このスキルが足すのは、利用者が決めるところと、出す前に止まるところ。

## 始める前に確かめること

1. `redmine` スキルで、そのバージョンに紐付いたチケットを調べる。**終わっていないものが残っていれば、利用者に伝える**
2. リリースのチケット「0.x.y を出す」(サポート) を作る。作ったもの、確かめたことはここに書く
3. 利用者に番号付きで尋ねる
   1. **ストア版を出すか**。ストア版に効く変更が無いときは出さない (利用者が決める)。効くかどうかの判断材料を添える (例: exe の隣の DLL の直しは、ストア版には効かない)
   2. **バージョンの番号**。機能の追加か、直しだけか

## 利用者が決めるところ

取り消しにくく、外に見えるものなので、ここは必ず止まる。

| 止まるところ | 理由 |
|---|---|
| リリースノートの下書きをチケットに書いたあと | 利用者が書き直した文をそのまま使う。**言い換えない** |
| `git tag` と `git push origin v0.x.y` の前 | タグは公開される |
| `gh release create` の前 | 公開される。出したものを消しても、取得された exe は残る |
| Store の「送信して認定を受ける」 | **利用者が押す**。代わりに押さない |

一度の了承を次の段階へ広げない。リリースノートの了承は、公開の了承ではない。

## ビルドの確かめ方

コミットしたあと**何もファイルを変えずに** `build.cmd -Msix` (Store に出さないときは `build.cmd`) を実行し、すぐに次を走らせる。

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .claude\skills\release\scripts\Test-ReleaseBuild.ps1
```

「変更あり」でないこと、リビジョンが今のコミットと同じこと、バージョンが揃っていることを確かめ、大きさと SHA-256、同梱する .NET を出す。出た値をリリースのチケットに書く。

**NG のビルドは配らない**。「変更あり」のビルドは、報告を受けても元のソースを再現できない。直してコミットし、ビルドからやり直す。

`build.cmd` の最後の DLL の確認ツールが NG のときも同じ。DLL の確認ツールは Expzip のウィンドウを 2 回出すので、走る前に利用者に伝える。全テスト (`tests\ui\Run-UiTests.ps1`) のときは「マウスとキーボードに触らないでください」と伝える。

## リリースノート

形は前のリリースにそろえる。`gh release view v<前のバージョン>` で読む。

- 「修正点」「セキュリティの修正」「変更点」の見出しに分ける
- README だけの変更や、言葉をそろえただけのものは書かない
- 利用者の言葉で書く。**チケットの番号と開発の言葉は入れない**
- **公開しないと決めた話と、セキュリティの攻撃の手順は書かない**
- 「0.x.y からの変更」は、前に出したバージョンから数える。ストア版だけ出していなかったときは、ストアの「このバージョンの最新情報」はストア版の前のバージョンから数える

## 出したあと

1. 上がった exe の大きさと SHA-256 が手元と同じことを確かめる
2. Store に出すときは認定を待つ。認定に通るまで、リリースのチケットとバージョンは閉じない
3. 認定に通ったら (Store に出さないときは GitHub に出したら)、リリースのチケットとバージョンを終了にする
4. 「出したら閉じる」としていたチケットを閉じる
