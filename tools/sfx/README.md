# 自己解凍書庫の取り出し部 (sfx)

自己解凍書庫の作成 (#29) で、書庫の前に付ける小さな Win32 実行ファイル。
自分自身の後ろに繋がれた ZIP を読み、中身を取り出す。

受け取った人が Expzip を持っていなくても中身を取り出せるようにするためのもの。

## 出来上がりをリポジトリに置いてある理由

`src/Expzip/Resources/sfx-x86.exe` (8,704 バイト) を同梱してある。**Expzip 本体をビルドするのに
C のツールチェーンは要らない。** `dotnet build` だけで通る。連結プログラム (`tools/joiner`) と
同じ考え方で、理由もそちらの README に書いてある。

読める形で残すために `sfx.c` を同じ場所に置いてある。バイナリだけを信じてもらう必要はない。

## 伸長器を内蔵している理由

**Windows は deflate を配っていない。**

実体はある。`C:\Windows\System32\archiveint.dll` が **Windows-internal libarchive library**
(libarchive 3.8.4) で、`tar.exe` とエクスプローラーの「圧縮フォルダー」(`zipfldr.dll`) が
これを使っている。

しかし名前のとおり internal で、Windows SDK にも文書にも無く、互換性の約束もない。しかも
`tar.exe` が Windows に入ったのは 10 の 1803 から。**自己解凍書庫は受け取った人の環境で動く
必要がある**ため、この道は採らない。

他のソフトも内蔵している。7-Zip は伸長を貸す DLL を1つも読み込んでいない
(`OLEAUT32` / `USER32` / `ADVAPI32` / `msvcrt` / `KERNEL32` のみ) のに zip を展開できる。
zlib の文字列も無いので、zlib ですらなく自前の実装。

参考までに 7-Zip の自己解凍モジュールは `7z.sfx` が 214,528 バイト、`7zCon.sfx` が
193,536 バイト。どちらも LZMA を解くもので、こちらは deflate だけなので小さく収まっている。

## 書庫の位置の求め方

Expzip はこの実行ファイルの後ろに ZIP を**そのまま繋ぐ**。中央ディレクトリの位置は
書き換えない。前に付いた分のずれは終端レコードから逆算できる。

    書庫の開始位置 = 終端レコードの位置 - 中央ディレクトリの大きさ - 中央ディレクトリの位置

中央ディレクトリは終端レコードの直前で終わっているため、この式で求まる。読み取り側 (#32) が
使っているのと同じ計算で、7-Zip も同じように開ける。

## ビルドし直す方法

`sfx.c` を直したときだけ、`build.cmd` を走らせる。
出来上がりは `src/Expzip/Resources/sfx-x86.exe` へ自動で複写される。

    tools\sfx\build.cmd

要るもの: Visual Studio 2022 の C++ ワークロード (`cl.exe` と `link.exe`)。

## 決めごと

- **x86 でビルドする。** 32bit と 64bit のどちらの Windows でも動くため
- **C ランタイムを使わない。** 使うと 100KB を超える
- **署名しない。** 署名証明書を持たないため。SmartScreen の扱いは #60 のノートを参照
- **取り出し先は、自分と同じ場所に自分の名前で作るフォルダ。** 尋ねる画面は持たない
- **`-q` を付けると黙って動く。** 自動での確認に使う
- **扱うのは 格納 と deflate だけ。** パスワード付きと ZIP64 は、作る側 (`SfxWriter`) が
  先に断るため、ここには来ない。それでも来た場合は、黙って壊れた結果を出さずに数え上げて報告する
- **書庫の中の名前が取り出し先の外を指していたら飛ばす。** `..` や絶対パスを弾く (Zip Slip 対策)
- **CRC と展開後の大きさを照らし合わせる。** 合わなければその1件を消して、失敗として数える
